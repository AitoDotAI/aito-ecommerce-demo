# ADR 0012: Feedback — multi-field `_predict` over review text

**Status:** Accepted
**Date:** 2026-05-12
**Deciders:** Antti

## Context

Support teams triage customer reviews manually: read each one,
decide the category (shipping / quality / fit / praise / question),
mark sentiment, assign to the right agent. Volumes are too low to
justify a dedicated classifier and too high to scale linearly
with team size.

`TASK.md` lists "feedback / churn" as the **Understand** section's
two views. This ADR is the Feedback half. The two views ship in
one PR.

The view's job: turn a free-text review into four structured
fields with confidence chips in one round-trip. Same fanout
pattern as Product Filling (ADR 0009), applied to text instead
of structured product attributes. The fourth field is the
forward-looking churn-risk signal — connecting feedback to
retention (see ADR 0013).

## Aito usage

Four parallel `_predict` calls against the `reviews` table,
each conditioning on the review's `text` Text column:

```json
{
  "from": "reviews",
  "where": { "text": "Package arrived late. The seal was broken." },
  "predict": "category"
}
```

```json
{
  "from": "reviews",
  "where": { "text": "Package arrived late. The seal was broken." },
  "predict": "sentiment"
}
```

```json
{
  "from": "reviews",
  "where": { "text": "Package arrived late. The seal was broken." },
  "predict": "assigned_to"
}
```

```json
{
  "from": "reviews",
  "where": { "text": "Package arrived late. The seal was broken." },
  "predict": "churn_within_90d"
}
```

Each returns `$p` + `feature` + `$why`. Aito tokenises the Text
column on whitespace; the `$why` per prediction surfaces which
tokens contributed most lift. The Boolean `churn_within_90d`
predict's `$p` is the headline number — "P(this reviewer
churns within 90 days)" — and the page renders it as a colored
risk bar (red ≥ 50%, yellow 25-50%, green < 25%).

## Decision

### New `reviews` table

5 string + int columns + one Text column for the body:

| Column | Type | Notes |
|---|---|---|
| `review_id` | String | PK |
| `customer_id` | String, link → customers | Anchors to a real customer |
| `product_sku` | String, link → products | Anchors to a real product |
| `rating` | Int | 1–5 stars |
| `text` | Text, whitespace | The body — the `_predict` conditioning column |
| `category` | String | shipping / quality / fit / praise / question |
| `sentiment` | String | positive / negative / neutral |
| `assigned_to` | String | The support-team member who took it |
| `created_at` | String | YYYY-MM |
| `churn_within_90d` | Boolean | True iff reviewer has no orders in 3 months after review |

`reviews.json` is generated by `data/generate_fixtures.py` —
~2,000 rows, each anchored on an existing `(customer_id,
product_sku)` pair from the order history. Templates per category
fill from a slot-based vocab; rating is conditioned on category
(praise → 4-5★, quality / shipping complaints → 1-3★).

### Service shape

`src/feedback_service.py` mirrors `src/filling_service.py`'s
fanout. Three parallel `_predict` calls in a `ThreadPoolExecutor`,
total wall-time ~250-400 ms warm.

The frontend (`frontend/app/feedback/page.tsx`) renders a
two-column layout: incoming review on the left (with rating,
text, customer + product context), predicted fields on the right
(value + confidence chip + ground-truth match indicator).

Ground-truth `category` / `sentiment` / `assigned_to` are stored
on the review (they're part of the demo's labels), so the UI can
render a "✓ matches stored" or "≠ expected" pill next to each
prediction. CLAUDE.md prime directive #2 — show the honest
comparison, don't paper over mismatches.

## Acceptance criteria

- [x] A user can open `/feedback` and see one review's text + three
      predicted fields rendered with confidence chips.
- [x] Each prediction shows a match indicator against the stored
      ground-truth value.
- [x] Switching the review picker re-runs the three predicts and
      updates the cards.
- [x] The Aito panel shows the three predict bodies (with the
      `predict` field cycling).

## Demo impact

Adds the **Understand** sidebar section's first view. Doesn't
disturb the five existing demo moments — Feedback is additive.

The narrative arc: Smart Search (rank flip) → For You (persona
switch) → Bought Together (lift) → Product Filling (5 fields) →
Evaluation (honest failure) → **Feedback (text triage)** →
**Churn (who's leaving)**. Two new beats on the "understand the
customer" axis.

## Out of scope

- **OCR / image attachments**. Reviews are text-only here.
- **Multi-language detection**. The fixture is English.
- **Reply drafting**. Aito predicts the assignment; the agent
  writes the response. A follow-up could use `_recommend` over
  past resolved tickets to suggest a reply.
- **Sentiment drift over time**. The view is per-review;
  per-product or per-month sentiment trends belong in Pattern
  Explorer or a new analytics surface.

## Consequences

**Good:**
- Demonstrates Aito's Text-column predictions naturally — text-in,
  structured-fields-out is a very common e-commerce task.
- Reuses Product Filling's fanout pattern, so it's the second
  worked example of "three parallel predicts in one round-trip".
- Adds review data the rest of the demo can later use (e.g.
  "products with the lowest avg rating" via `_search` aggregation).

**Bad:**
- Adds ~2,000 rows + a new table to the Aito DB — load time +
  ~100 KB of JSON. Acceptable on the free tier.
- The deterministic mapping `category → assigned_to` makes the
  `assigned_to` prediction trivial for Aito (95%+ accuracy). We
  could engineer mis-assignments but kept the clean mapping for
  the demo's narrative (Aito learns the support team's de-facto
  workflow).

## Notes

The text-template approach for fixture generation is borrowed
from `aito-accounting-demo`'s invoice-description generator. The
key constraint: per-category templates must be distinct enough
that token overlap is rare — otherwise Aito's prediction degrades
because the conditioning column carries no discriminative
information.
