# ADR 0006: Smart Search — predictive re-ranking

**Status:** Accepted
**Date:** 2026-05-11
**Deciders:** Demo team

## Context

Smart Search is the load-bearing demo moment: a single query, side
by side, shows what changes when Aito's predictive context is wired
in. `TASK.md` writes it as:

> Side-by-side standard vs. predictive results for the query "food"
> with a large-breed dog-owner context. **Cat food drops from rank 1
> to rank 6** because the customer has never bought cat products.
> _This is the strongest visible-aha moment in the demo. Do not
> weaken it._

Two things from the live probe forced an honest adaptation of that
literal framing:

1. **Catalog skew dictates baseline.** PetNord's catalog has more
   dog-food SKUs than cat-food SKUs (Acana / Orijen / Eukanuba make
   dog food, not cat; Royal Canin / Hill's split). So token-only
   `_search` for "food" ranks Royal Canin **dog** food at the top
   by default — *not* cat food. The "cat food drops from rank 1 to
   rank 6" framing doesn't fit the data.

2. **The real moment is stronger.** With the right query, cat food
   appears in **rank 1–8 for a cat owner** and drops completely out
   of the top 10 for a large-breed dog owner. *Same query string,
   same baseline rank, completely different predictive list.* That
   reads as "Aito learns the customer" rather than "Aito moves an
   item from rank 1 to rank 6", which is a sharper sales narrative.

## Aito usage

### Baseline (left column) — plain `_search`

```json
POST /api/v1/_search
{
  "from": "products",
  "where": { "name": { "$match": "food" } },
  "limit": 10
}
```

Aito's `_match` operator tokenises the `Text` column and returns
hits ranked by token-overlap score. The catalog skew shows here:
top-10 reads as dog-heavy. This is the "honest baseline" — what a
non-predictive shop's search engine would return.

### Predictive (right column) — `_recommend` with segment goal

```json
POST /api/v1/_recommend
{
  "from": "order_lines",
  "where": {
    "product_sku.name": { "$match": "food" }
  },
  "recommend": "product_sku",
  "goal": {
    "customer_segment": "dog_owner",
    "customer_pet_size": "large"
  },
  "limit": 10
}
```

Semantics: "rank products matching the query string by
`P(this segment | a line containing this product)`." Products that
this segment *has historically bought* float to the top because
their conditional probability under the segment is high.

For `customer_pet_size`, we use `null` when not applicable (cat
owners, etc.) — Aito treats absent as a wildcard and the goal
collapses to `{customer_segment: ...}`.

### Verified live (2026-05-11, after schema migration)

| Persona              | Top-3 categories | Sample product |
|---|---|---|
| Maija — cat_owner    | cat × dry-food, cat × dry-food, cat × dry-food | "Acana Turkey Cat Food 12kg"  (p ≈ 0.91) |
| Olli — multi_pet     | dog × dry-food, cat × dry-food, dog × wet-food | (mixed) |
| Saara — dog_owner / large | dog × dry-food, dog × dry-food, dog × dry-food | "Acana Beef Dog Food 1kg" (p ≈ 0.51) |

### Schema migration this ADR requires

`_recommend` from `order_lines` only does **single-hop link
traversal** — `order_id.<orders col>` and `product_sku.<products
col>`. Reaching `order_id.customer_id.<customers col>` returns 400
("field not found"). So we **denormalize** the two demo-load-bearing
customer attributes down to the line level:

```python
"order_lines": {
    ...
    "customer_segment":  {"type": "String", "nullable": False},
    "customer_pet_size": {"type": "String", "nullable": True},
}
```

Generated by `data/generate_fixtures.py` at the same time as the
underlying customer is selected for the order. Both columns sit on
the same row as the link to the product — Aito's `where` and `goal`
clauses read them directly without a join.

This is the same denormalisation pattern the `aito-erp-demo`
`assignments` table uses for `project_type` and `project_success`,
and the same one the framework doc encourages when single-hop
queries need cross-table attributes.

## Decision

### UI structure

```
┌── Customer pill row ───────────────────────────────────────────┐
│  ◉ Maija (cat owner)    ○ Olli (multi-pet)    ○ Saara (large dog) │
└────────────────────────────────────────────────────────────────┘

┌── Search bar (default "food") ─────────────────────────────────┐
│  🔍  food                                              [Search] │
└────────────────────────────────────────────────────────────────┘

┌── Standard ─────────────┐  ┌── Predictive ───────────────────┐
│  10 results              │  │  10 results · Saara             │
│  1. Royal Canin Dog Food │  │  1. Acana Large Breed Lamb …    │
│  2. Royal Canin Dog Food │  │  2. Hill's Sci Plan Puppy …     │
│  3. Royal Canin Dog Food │  │  3. Eukanuba Large Breed Beef … │
│  …                       │  │  …                              │
└──────────────────────────┘  └─────────────────────────────────┘
```

Each row shows:
- Product name + brand
- `pet_type` chip (dog / cat / aquarium / …)
- A **rank-delta** chip on the predictive side:
  - `↑ N` (rose) if rank improved by N from baseline
  - `↓ N` (slate) if rank fell
  - `★` (gold) if not in baseline top 10 (new entry — strongest visual)
  - `—` if unchanged

The delta chip is the demo-moment visual. A Maija → Saara switch
flips many `↑` to `↓` and surfaces 4–8 `★` per side.

### Response DTO

```ts
interface SmartSearchHit {
  sku: string;
  name: string;
  brand: string;
  pet_type: string;
  category: string;
  price_eur: number;
  rank: number;
}

interface SmartSearchHitWithDelta extends SmartSearchHit {
  /** Rank delta vs. the other side. Negative = improved. */
  delta_rank: number | null;
  /** True when this product was NOT in the other side's top-N. */
  new_entry: boolean;
}

interface SmartSearchResponse {
  query: string;
  customer: { id: string; label: string; segment: string; pet_size: string | null };
  baseline: SmartSearchHit[];
  predictive: SmartSearchHitWithDelta[];
  last_query: { endpoint: string; body: object };
  last_response_ms: number;
}
```

### Endpoint

`GET /api/smart-search?q=<query>&customer=<persona_id>`

Persona ids: `maija` → CUST-00001 / cat_owner / null, `olli` →
CUST-00002 / multi_pet / small, `saara` → CUST-00003 / dog_owner /
large. The frontend pill bar maps friendly labels to the underlying
segment / size tuple; the backend never sees a raw customer id beyond
the three demo personas (per CLAUDE.md: no PII, customer_id is
already anonymous).

Cached per `(query, customer)` for 5 minutes.

- [ ] **Maija** (cat_owner): predictive top-10 is ≥ 70 % cat

## Demo impact

This is **demo moment #1** in `TASK.md`'s five-moment list. Done
right, it sells the whole demo: switching the persona pill flips
the entire grid live, the Aito panel shows the exact query body
that drove it, the delta chips make the change quantifiable.

## Out of scope

- Per-customer (`order_id.customer_id`) personalisation — segment
  conditioning already produces the moment; per-customer adds
  complexity without sharpening the visual.
- Free-text customer input — the three persona pills cover the
  demo path. Visitors who want to type-in a customer go to For You.

## Consequences

**Good:**
- The query shape generalises: future For You / Bought Together can
  reuse the same `_recommend ... goal: segment` pattern. The cheatsheet
  entry is the load-bearing reusable building block.
- The schema migration is small (two columns), reversible, and
  immediately useful for anything that needs to filter or
  conditional-rank by customer segment from `order_lines`.

**Bad:**
- Two-line denormalisation means `customer_segment` and
  `customer_pet_size` on `order_lines` must stay in lock-step with
  `customers.<same>` for the same `customer_id`. If a customer's
  segment ever changed mid-fixture-window, we'd ship a stale value.
  The generator handles this (segment is set at customer creation),
  but a real-world version would need a refresh on segment change.
- The literal "rank 1 → rank 6" framing in `TASK.md` is not what
  the data + Aito produce. We adapt to "same query, totally
  different list per persona" — which is a stronger moment, but a
  reviewer comparing the demo to TASK.md verbatim will want the
  difference flagged in the demo-script. ADR notes the adaptation
  explicitly.

## Notes

- The `goal` parameter is the load-bearing knob. With
  `goal: {returned: False}` the customer-context signal washes out
  (returned is uniform across products at 97 %), so the ranking
  doesn't differentiate. `goal: {customer_segment: X}` makes the
  segment the differentiator. Recorded in the cheatsheet so the
  next implementer doesn't repeat the cycle.
- We do **not** filter `aquarium_owner` for this demo's pill bar
  (aquarium owners essentially never search "food", and the
  predictive list collapses to obscure picks). Adding them would
  make the demo read as broken for one pill — not worth it.
