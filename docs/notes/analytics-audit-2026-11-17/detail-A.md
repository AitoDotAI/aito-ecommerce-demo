## Routing facts (so the views are the right ones)
- `/customers` -> frontend/app/customers/page.tsx (components in frontend/components/customers/*). API: src/customer_profile_routes.py.
- `/shop-analytics` is a MOVED route: forwards to `/patterns/` (frontend/lib/moved-routes.ts:20). The page is frontend/app/patterns/page.tsx; API keeps the `/api/shop-analytics/{funnel,who,baskets,search-words}` paths (src/app.py:675-715).
- `/purchase-analytics` is a MOVED route: forwards to `/` = Overview (frontend/lib/moved-routes.ts:42: "Purchase Analytics' trend and best sellers are on the Overview"). So its numbers live in frontend/app/page.tsx + components/overview/OverviewParts.tsx, API `/api/overview` (src/overview_service.py, src/overview_headlines.py, src/household_cards.py).

## Aito capability evidence used below (what Aito can do today)
- v2 SQL `POST /api/v2/_sql`: `count(*)`, `sum`, `avg`, `min`, `max`, `count(DISTINCT col)` (sole select item only), scalar arithmetic in select/where, `GROUP BY` ONE column with per-group count/sum/avg only (no per-group min/max), `HAVING`, `ORDER BY`, `INNER JOIN` along a declared link only. core/docs/sql-support.md sections "Supported grammar", "GROUP BY", "count(DISTINCT col)", "Computed columns", "Aggregate expressions", "JOIN (along an existing link)".
- Multi-column `GROUP BY a, b` works but is evaluated in memory (a scan of the `from` selection): core/docs/sql-support.md "Multi-column GROUP BY".
- NOT in v2 SQL: window functions, subqueries, outer joins, UNION (core/docs/sql-support.md "Not supported yet"); "an aggregate expression with GROUP BY" is rejected (same file, "Computed columns" Notes).
- No median / percentile / stddev / variance keyword in v2 SQL (grep of core/docs/sql-support.md, aito-sql-dialect.md: none) -> "unverified" for SQL; but `_aggregate` returns `$mean` with `.samples/.variance/.standardDeviation/.standardError` (docs/aito-cheatsheet.md:948-985, "_aggregate"; core/api-docs/content/query-reference-v2.md:498 lists `$sum`/`$mean (+ variance stats)`/`$min`/`$max`).
- `_relate`: lift plus counts `fs` {fOnCondition, fCondition, f, n} (docs/aito-cheatsheet.md:530-545). It returns NO interval; the intervals come from app code `lift_interval` (src/price_bands.py:32). No doc in core/docs or core/api-docs/content mentions a confidence/credible interval on `_relate` hits (grep "interval" hits only benchmark prose) -> an interval on `_relate`/`_aggregate` lift is an engine gap (unverified whether one is planned).
- Bootstrap: grep for "bootstrap" in core/docs and core/api-docs/content finds nothing -> no bootstrap feature documented. `_aggregate $mean` gives `standardError`, a normal-theory alternative (cheatsheet:972-975).
- `_evaluate` / `_estimate` also exist as SQL table functions (core/docs/sql-support.md "evaluate(...) and estimate(...)"), though the same file's "Roadmap > Still open" still lists them as open: the doc contradicts itself (unverified which is current).
- `_aggregate` cannot go in `_batch` (cheatsheet:1039-1040).
- Does Aito hold the source rows? Yes for most: tables customers (total_spent_eur, total_orders, churned, pets...), orders, order_lines, customer_actions (purchased_30d, spend_30d_eur, cost_eur), nps_responses, reviews, impressions, contexts, customer_months, products, product_states (src/schema.py:58, 465 and others). The Customers view does NOT read them from Aito at runtime.
